How split_clients works

      
    
        
  1. Build the key. Nginx expands the first argument (for example $request_id or $remote_addr) into a string for this request.
    2. 
        
  2. Hash it. The string is hashed with MurmurHash2 into a number from 0 to 4,294,967,295.
    3. 
        
  3. Find the bucket. Percentages are stacked into ranges over that number space. 50% owns the first half; * owns whatever is left. The first range that contains the hash wins, and its value is stored in $split_target.
    4. 
        
  4. Route. The map copies $split_target into $route, unless the request carries an X-Canary header that forces a side. proxy_pass http://$route then sends the request to that upstream.
    5. 
        
  5. Fall back. If the chosen upstream answers 502, 503 or 504 (for example because the New Nginx is stopped), error_page … = @legacy retries the request on the Legacy side.
    6. 
      

      
Sticky or not?

      
The key decides. $request_id is random for every request, so each request is an independent coin flip. $remote_addr, $arg_user or $http_x_user stay the same for a client, so that client always lands in the same bucket until the percentages change.

      
Why two "Legacy Nginx" lifelines?

      
The Legacy Nginx plays two roles in one process: the front door that clients connect to, and the legacy application on 127.0.0.1:8080. A request routed to legacy_nginx leaves the front door and comes straight back into the same Nginx as a second request.
